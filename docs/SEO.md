# SEO & GEO: entity resolution for a domain with a hoax in its past

The canonical production origin is **https://globalparadigmscorp.com**.

This domain has a history it did not choose. From 2006 until this site was rebuilt, the only thing the web
said about `globalparadigmscorp.com` was that it had been a **fan-made hoax** during _The Lost Experience_
— documented on Lostpedia, in contemporaneous clue blogs, and in academic writing about ARGs. Ask a
generative engine "what is globalparadigmscorp.com" and the correct answer, absent input from us, is the
2006 one.

So the job here is not "rank for keywords". It is **entity resolution**: be the clearest, most citable
statement of what this URL is _now_, while confirming — not denying — what it was. SEO gets the page
found; GEO (generative engine optimisation) gets it _quoted_, which means being the most extractable,
least ambiguous answer about the entity.

- **SEO** — rank for `global paradigms corp`, `lost arg hoax`, `hanso foundation website`,
  `globalparadigmscorp.com`, `new arg 2026`.
- **GEO** — state the complete answer once, up front, dated, disambiguated, in a form a model can lift
  without merging two unrelated things into one.

## The copy, and the one place it lives

| File                        | Holds                                                                                               |
| --------------------------- | --------------------------------------------------------------------------------------------------- |
| `src/config/seo-copy.ts`    | The prose: both eras, the FAQ, the fact table, the `/legacy` narrative. **Import-free** on purpose. |
| `src/config/seo-pages.json` | The route manifest: one title, heading and description per canonical URL.                           |
| `src/config/seo.ts`         | Routing-aware helpers (`routeSeo`, `canonicalUrl`) + re-exports. The single import point.           |
| `src/config/site.ts`        | `SITE` (name/title/description/studio) and `FICTION_NOTICE`.                                        |

`seo-copy.ts` imports nothing so that (a) the Node tsconfig project can typecheck `src/tests/seo.test.ts`
without a DOM, and (b) `scripts/lib/load-seo.mjs` can bundle it with esbuild without dragging React in.
Anything that needs the router — `SECTION_INDEX`, `routeSeo()` — lives one file up in `seo.ts`. The
studio/OS/name values inside the copy are therefore literals, and `seo.test.ts` pins them to `SITE`.

**Never hand-edit a generated surface.** Edit the copy, regenerate, let the tests confirm.

## Why the crawlable block exists: the crawler matrix

| Crawler                                                     | Executes JavaScript | Before this layer it saw             |
| ----------------------------------------------------------- | ------------------- | ------------------------------------ |
| Googlebot (Search)                                          | Yes (renders)       | the rendered app after a second pass |
| Bingbot                                                     | Yes                 | the rendered app                     |
| **GPTBot** (OpenAI training)                                | **No**              | an empty `<div id="root">`           |
| **OAI-SearchBot** (ChatGPT search)                          | **No**              | an empty `<div id="root">`           |
| **ClaudeBot / Claude-SearchBot**                            | **No**              | an empty `<div id="root">`           |
| **PerplexityBot**                                           | **No**              | an empty `<div id="root">`           |
| **CCBot, Amazonbot, Applebot-Extended, Meta-ExternalAgent** | **No**              | an empty `<div id="root">`           |

Every engine that does not render JavaScript could previously read exactly one thing about this site: that
it was blank. The block closes that gap. It is real HTML inside `#root`, so it also fills the black screen
while the bundle downloads, and React replaces it on mount — the player never sees it.

The block is **route-aware**: `/` and `/legacy` carry the whole record (lede → fact table → both eras →
quotes → invented staff → FAQ → section index → fiction notice); every other route carries its own
heading and description plus the full section index. Nineteen copies of the homepage would be a doorway
pattern; nineteen summaries of one work is a corpus.

## The five surfaces that must not disagree

1. **`index.html` head** — title, description, canonical, robots, Open Graph, Twitter.
2. **The crawlable block** — the answer in prose, rows and questions, for non-rendering engines.
3. **JSON-LD** — the same facts in structured form, plus the two deliberate omissions below.
4. **Discovery files** — `robots.txt` (welcomes 18 generative crawlers by name), `sitemap.xml` (exactly
   the routed sections), `llms.txt` (a one-page brief).
5. **The app** — `SITE.title`, `RouteMetadata`'s live head, and `/legacy`.

## The two-era copy rules

1. **Both eras, one sentence each, dated.** "Era I (2006) … online from at least 20 April 2006 and offline
   by 30 July 2006." "Era II (2026) … reopened." No hedging, no "some say".
2. **"At least" is doing real work.** 20 April 2006 and 30 July 2006 are the earliest and latest
   _documented_ sightings (Lostpedia), not the true launch and takedown. The copy says so; the FAQ says so.
3. **Non-affiliation travels with the names.** _Lost_, ABC, Disney, the Hanso Foundation and the Valenzetti
   Foundation appear because they are the historical record of this URL — every surface that names them
   also states, in the same breath, that the 2026 work is not affiliated with them.
4. **Never present Era I as official.** The 2006 page was a hoax; saying so is both accurate and the
   strongest possible disambiguation.
5. **Fiction is stated before the mystery.** The first words a model reads about this site say it is
   invented. The premise comes after.

## JSON-LD: two deliberate choices

- **There is no `Organization` node for "Global Paradigms Corp."** The company is a work of fiction.
  Marking it up as a business entity would teach engines to answer as if a real corporation existed — the
  exact hallucination the 2006 page produced in human readers. The one `Organization` node is the real
  publisher, Zazie Productions; the fictional company is a `CreativeWork` with a
  `disambiguatingDescription`. A test fails if a second `Organization` appears, and `verify-dist.mjs`
  enforces it on the built artifact too.
- **`subjectOf` points at the external record.** The `CreativeWork` carries a `subjectOf` to Lostpedia's
  article on the 2006 hoax, so an engine has both eras in view and a reason not to merge them.

The graph is `WebSite`, `Organization` (publisher), `CreativeWork`, `WebPage`, `FAQPage`. Ignoring CSP:
JSON-LD data blocks are not executed, but the hash is generated from the exact script text anyway, because
generating it costs nothing and forgetting it silently breaks structured data.

## robots.txt, sitemap.xml, llms.txt

- **robots.txt**: everyone allowed; nothing here is private (clearance tiers are a game mechanic enforced
  in the browser, not access control). Eighteen generative crawlers are welcomed by name, each in its own
  group with an explicit `Allow: /`, because a crawler matched by a named group does not inherit `*`.
- **sitemap.xml**: exactly the routed sections, in navigation order with `/legacy` first, no `<priority>`
  or `<changefreq>` (search engines ignore both), no `?record=` / `?doc=` deep links — those are modal
  states and canonicalise onto their section.
- **llms.txt**: honest about itself. Google's generative-search guidance says it ignores the file; it
  ships because it costs one static file, several non-Google tools read it, and it is the shortest place
  to state the two rules that matter when this site is summarised: **it is fiction**, and **the two eras
  are not one work**. It also tells models that puzzle answers are deliberately absent.

## Franchise names: the decision, on the record

Naming _Lost_, The Lost Experience, the Hanso Foundation and the Valenzetti Foundation was a deliberate
product decision. Those are the highest-value queries attached to this domain, and the use is
historical/descriptive — identifying what this URL was twenty years ago, which is a matter of public
record — while every surface that names them also carries an explicit non-affiliation.

This is a judgement call, not a legal opinion. If the positioning ever needs to change, it changes in
`src/config/seo-copy.ts` (the `ERA_ONE` block and `ANSWER_FIRST`) and propagates everywhere via
`npm run seo:render && npm run seo:generate`; the tests will not let a surface lag behind.

## Changing routes or metadata

1. Add or update the route in `src/config/navigation.ts` and `src/app/router.tsx` as usual.
2. Add matching metadata in `src/config/seo-pages.json` (title 30–65 chars, description 110–165 chars,
   both unique — the generator enforces this).
3. If public content changed materially, update `site.lastModified` to the actual change date.
4. Regenerate and verify:

   ```sh
   npm run seo:render      # index.html's generated regions + the CSP hash
   npm run seo:generate    # public/sitemap.xml, robots.txt, llms.txt
   npm run check           # typecheck → lint → tests → seo:check → build → verify:dist
   ```

Keep legacy URLs out of the sitemap and add permanent redirects to both `vercel.json` and
`public/_redirects` when a canonical route is renamed. The sitemap's `lastmod` should represent a
meaningful public content change, not deployment time.

If the canonical hostname changes, update `CANONICAL_ORIGIN` in `seo-copy.ts` and `site.origin` in
`seo-pages.json` (the generator fails if they disagree), regenerate, and update the hand-written head in
`index.html`.

index.html is listed in `.prettierignore`: the CSP hash is over bytes, so the file must not be reformatted
by an unrelated tool.

## When production serves HTML for a discovery file

Symptom: Search Console reports **"Sitemap could not be read"**, `curl -sI https://globalparadigmscorp.com/sitemap.xml`
answers `Content-Type: text/html`, and opening the URL shows the application instead of raw XML. The files
are valid — the deployed revision or the edge routing is not. Check in this order:

1. **Is the deployed revision current?** Compare the live deployment's commit with `main`. The host's build
   settings must be build command `npm run build`, output directory `dist`, production branch `main`.
2. **Did the artifact keep the discovery files?** `npm run build` finishes with `verify:dist`, which fails
   when `dist/sitemap.xml` is HTML, `dist/robots.txt` is missing or disallows crawling, a route entry point
   is absent, an entry point carries no crawlable block or JSON-LD, `llms.txt` lost the non-affiliation,
   or `dist/_redirects` contains a catch-all rewrite. It can also be run alone against any build output:
   `npm run verify:dist -- --dist <dir>`.
3. **Is a catch-all rewrite shadowing the files?** Remove `/*  /index.html  200` from `_redirects` **and**
   from any hosting-dashboard rule. Every canonical route ships a static entry point, so the rule is not
   needed; while it is active, unknown paths answer `200` as well, which turns real 404s into soft 404s.
4. **Is the edge cache serving the old response?** Purge the CDN cache for `/`, `/sitemap.xml` and
   `/robots.txt` after deploying, then confirm the raw responses:

   ```sh
   curl -s https://globalparadigmscorp.com/sitemap.xml | head -2   # <?xml version="1.0" ...
   curl -s https://globalparadigmscorp.com/robots.txt | head -2    # User-agent: * / Allow: /
   curl -s https://globalparadigmscorp.com/legacy | grep -o '<title>[^<]*'   # the two-era title
   ```

Only once those commands print XML and plain text should the failed sitemap entry be removed in Search
Console and `https://globalparadigmscorp.com/sitemap.xml` resubmitted. Submit the apex hostname only:
`www.globalparadigmscorp.com` does not resolve, and a `www` property would collect errors instead of pages.

## Google Search Console relaunch checklist

After deploying the build:

1. Confirm the apex domain uses HTTPS. `www` is not served at all today — do not submit it; add a
   `www → apex` redirect only once that hostname actually resolves.
2. Open these URLs without authentication and verify they return `200`:
   - `https://globalparadigmscorp.com/robots.txt`
   - `https://globalparadigmscorp.com/sitemap.xml`
   - `https://globalparadigmscorp.com/llms.txt`
   - `https://globalparadigmscorp.com/legacy`
   - `https://globalparadigmscorp.com/documents`
3. Verify a made-up URL returns `404`, not `200`.
4. In the **Domain property** for `globalparadigmscorp.com`, go to **Indexing → Sitemaps** and submit
   `https://globalparadigmscorp.com/sitemap.xml`. Remove obsolete sitemap submissions.
5. Use **URL Inspection → Test live URL** on the home page. Check that crawling is allowed, the declared
   canonical is `https://globalparadigmscorp.com/`, and the rendered page contains the archive heading.
6. Request indexing for the home page, `/legacy` and `/sanctum`. The submitted sitemap handles the rest;
   repeatedly requesting every URL does not accelerate indexing.
7. Monitor **Page indexing** for `Blocked by robots.txt`, `Duplicate without user-selected canonical`,
   `Crawled — currently not indexed`, and soft-404 reports.

A sitemap helps Google discover and recrawl pages; it cannot guarantee indexing or rankings. Because this
domain has existed before, map an old URL to a new URL only when there is a genuine equivalent. Let
obsolete URLs return `404` (or `410` at the edge) rather than redirecting every historical URL to the home
page, which can create soft-404 signals.

## Known limits

- **Still an SPA, deliberately.** Full per-route prerendering was not built: the per-route entry points
  replace the head, the JSON-LD and the crawlable block, but the _rendered_ app still arrives with the
  bundle. The static block closes the citation gap without changing the one-cacheable-chunk design.
- **`/legacy` is out-of-world.** It is site copy, not an archive record: it never enters the normaliser,
  the search index or the export pipeline. Recording a hoax is not the same as continuing one.
- **No analytics, so no ranking feedback loop.** Search Console is the only measurement, and this repo
  cannot verify it: the checklist above is a runbook, not a claim about live data.
- **The 2006 quotations are transcriptions.** They are quoted as a historical record of the domain, from
  Lostpedia's article, with the source named at the quotation — not as an endorsement and not as restored
  content.
